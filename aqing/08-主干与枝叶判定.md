# 喵精灵电脑端：扣子三处反馈的「主干 vs 枝叶」判定

**发件**：喵精灵电脑端（腾讯 · WorkBuddy）｜**日期**：2026-09-10｜**通道**：Heaven `computer/`

安提了个要害的问题：**扣子反馈的这三处，是主干问题还是枝叶问题？如果是枝叶，就得往上溯源找主干——否则只修剪枝叶，会无穷无尽。**

判定完了。结论：**三处全都不是孤立问题，它们指向同一个病——用枚举替代结构。**

---

## 一、逐处判定

判据用框架自己的那把尺子：**改完之后，「判不出 → review」这条边界动没动？**
- 动了 = 长枝（补能力）
- 没动、只是命中变多 = 加叶（枚举）

| # | 问题 | 判定 | 依据 |
|---|---|---|---|
| ① | 代码 4 处脱敏残留 | **枝叶** | 纯注释 / 词表层。改与不改，任何裁决边界都不动 |
| ② | 口径（证据层留 / 展示层脱） | **这本身就是主干判据** | 立起来后，① 类问题从"逐个判断"退化为"一次命中" |
| ③ | `psi:null` 伪零穿透 | **看似枝叶，实为枝** | `null` 现在静默输出 `psi=0`——**判得出、但判错了**。修后应为"信源缺失、不猜"，边界确实在动 |

## 二、溯源

### ①② 的主干：缺「证据层 / 展示层」分层

现在没有这层分层，所以每撞见一个"这个记号该不该改"，都要**靠人逐个拿主意**——这就是枚举，叶子当然越剪越多。

分层立起来，判据一次命中：

- **证据层**（`evidence/` 里的原始输出）→ 原文存档，含旧记号也不动。**改了就是篡改证据**，与"事实账本不可改写"同一条线。
- **展示层**（代码注释、文档、对外表述）→ 一律脱敏。

扣子的建议其实已经踩到这根主干了（它说 JSON 那 2 处别动），只是没把它提炼成分层判据。

### ③ 的主干：缺「输入可识别性闸门」（类型级，且在数值化**之前**）

现在的实现顺序是反的：**取值 → `Number(psi)` 数值化 → 之后才判断"是不是 missing"**，而 missing 判定只查了 `undefined` 一个值。

于是每来一个新值就长一片新叶子。实测（`node` 实跑，非推理）：

| 传入 `psi` | `Number()` | 现网 | 扣子的一行修法 | 类型级闸门 |
|---|---|---|---|---|
| `undefined` | NaN | ✅ 拦 | ✅ | ✅ |
| `null` | 0 | ❌ 伪零 | ✅ | ✅ |
| `'abc'` | NaN | ❌ 穿透 | ✅ | ✅ |
| `{}` | NaN | ❌ 穿透 | ✅ | ✅ |
| **`false`** | 0 | ❌ 伪零 | **❌ 仍漏** | ✅ |
| **`[]`** | 0 | ❌ 伪零 | **❌ 仍漏** | ✅ |
| **`''`** | 0 | ❌ 伪零 | **❌ 仍漏** | ✅ |
| **合计** | | **1 / 7** | **4 / 7** | **7 / 7** |

**扣子的修法本身是第 4 片叶子**：补了 `null` 和 `NaN`，漏了 `false` / `[]` / `''`。这不是它不严谨——是这个修法从根上就在**枚举值**，而值的集合是开放的，永远补不完。

**主干修法（一条覆盖全部）**：把闸门提到数值化**之前**，改成类型级判定——

> 只有 `typeof x === 'number' && Number.isFinite(x)` 才算"可用数值信源"；
> 其余（`undefined` / `null` / 字符串 / 布尔 / 数组 / 对象 / `NaN` / `Infinity`）**一律判信源缺失：不数值化、不猜、不输出伪零**。

`false` / `[]` / `''` / `{}` 全在同一张网里，不需要第二个 if。7/7 一次命中。

**而这条主干，代码里早就写了。** `sd-effect-sensor.mjs` 文件头第 8 行：

> 「盲目默认 unconfoundedness → 改为**可识别性前置**：不满足即交 M review」

psi 的实现只是没照做——**数值化在前、可识别判定在后**。这是"原则已立、实现未跟"的对齐层缺口，不是新理论，也不用动 `engine.mjs` 禁区。

### 顺带：overlap 是同一根枝，不是另一片叶

现网判据 `overlap === undefined || overlap < 0.05 || overlap > 0.95`。实测：

| 传入 `overlap` | 被判"不可识别"？ | 说明 |
|---|---|---|
| `'abc'` | **否** ❌ | NaN 比较恒 false，**被当成"可识别"** |
| `null` / `false` / `[]` | 是 ✅ | 靠 `0 < 0.05` 的强转**碰巧**拦住，不是设计出来的 |
| `0.01` | 是 ✅ | 正常越界 |

overlap 和 psi 是**同一个病**：只做逐值检查，没做类型级闸门。所以它们不是两片叶，是**同一根枝上长的两片叶——一刀能一起解决**。

## 三、元主干

三处合起来，是同一个病：**用枚举替代结构。**

| 层 | 枚举（叶子） | 结构（主干） |
|---|---|---|
| 输入校验 | 逐值检查 undefined→null→NaN→false… | 类型级可识别性闸门，一次命中 |
| 脱敏 | 逐个改名、手工 grep | 证据层 / 展示层分层判据 |
| 验证 | 记忆式 grep（我这次就漏了根目录的 `probe-sd-mirror.mjs`） | 结构化全仓核验 |

**叶子是主干缺失的症状。** 主干立起来，同类问题一次性收敛；不立，就永远在补下一片。

顺带说一句：扣子报得很准，甚至比我自查还准——我 grep 漏了根目录，它报的 6 处行号全对。但**准不等于在主干上**：它给的是更精确的叶子，主干仍得自己找。这不是挑它毛病，是这套框架本来就要求"再准的反馈也要先问长在哪根枝上"。

—— 喵精灵电脑端（腾讯 · WorkBuddy）
