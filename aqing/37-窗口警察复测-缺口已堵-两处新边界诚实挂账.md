## 二、对 `evidence/police_lens.mjs` 的复测（本篇核心）

### 2.1 先说一个「镜头对错了层」的发现

`police_lens.mjs` 是这么取引擎的：

```js
import { WeiwenLawEngine, DEFAULT_RIGID_ANCHORS } from '../weiwen-law-dsh/src/core/engine.mjs';
```

**它直接 import 引擎，绕过了窗口。** 而警察门禁站在**适配层**（`src/index.js`）——它正好在 `engine.decideToolCall` 之前那一步。

⇒ 结论：**这份探针现在再跑，A/D 两行还会照旧显示 ❌**——不是缺口没堵，是镜头没照到警察站的窗口。这是「视角打在哪一层」的问题，不是判据问题。

要照到窗口，得走 `apply(ctx)` 注册的钩子。最小复现（我本轮就是这么测的）：

```js
const mod = await import('<repo>/src/index.js');
const handlers = {};
mod.apply({ on: (ev, cb) => { handlers[ev] = cb; }, tools: { register: () => {} } });
const pre = handlers['tools/pre-execute'];                 // ← 警察在这里
const out = await pre({ name: 'run_command', arguments: { command: 'rm -rf' } },
                      async () => ({ kind: 'next' }));
// out.kind === 'deny' && out.insufficient_evidence === true
```

## 三、复测同时测出两处新边界（诚实披露，**未擅改代码**）

这两处不是猜的，是上面同一轮实测里冒出来的。按纪律：**发现 → 实测 → 挂账 → 不擅动**。

### 边界一：误伤面 —— 常见只读命令会被门禁全部拦下

| 调用 | 引擎直调 | 过窗后 | 我预期 |
|---|---|---|---|
| `run_command{command:"git status"}` | allow | **deny · 证据不足** | 应放行 |
| `run_command{command:"npm test"}` | allow | **deny · 证据不足** | 应放行 |
| `run_command{command:"ls -la"}` | allow | **deny · 证据不足** | 应放行 |
| `run_command{command:"node -v"}` | allow | **deny · 证据不足** | 应放行 |
| `run_command{command:"pwd"}` | allow | **deny · 证据不足** | 应放行 |
| `run_command{command:"python -c \"print(1)\""}` | allow | **deny · 证据不足** | 应放行 |

**6/6 全中。** 根因很直白：

- `evidenceOf` 的触发条件是「**`args` 里存在 `command` / `path` / `url` 字段**」，不是「**这个调用是动作类**」。
- 于是凡是「有 `command` 字段、但目标隐式（= 当前工作目录）」的命令，一律被判「未外化具体作用对象」。
- 而这类命令恰恰是**日常绝大多数**：查状态、跑测试、列目录、看版本。

代码注释里写的意图是「仅对**动作类**调用缺目标时拦截」「无资源字段的（查询 / 自查类）放行，避免误伤」——意图是对的，**落点偏了一格**：用「字段名存在」代替了「动作是否具破坏性」。测试锁 5 条覆盖的是「有/无资源字段」，**没有覆盖「有 `command` 字段但目标是 cwd」这一类**，所以这个面没被锁住。

**为什么我不擅改**：候选修法都得碰红线——

- 用「破坏性动词表」收窄 → 就是**扩词表**，违安给适配层定的约束（不改判据、不扩词表）；
- 放宽门禁范围 → 是**安全 ↔ 误伤的取舍**，属根因层，得安拍板。

⇒ **挂账，交安拍板。** 修法候选与代价都摆在上面，谁都可复现。

### 边界二：抢戏 —— R 域被覆盖的命令，门禁先拦、law 被降级

| 调用 | 应该怎样 | 实际 | 差在哪 |
|---|---|---|---|
| `run_command{command:"git reset --hard"}` | 引擎 `deny / R` | **`deny / 证据不足`**（门禁先拦，未进引擎） | `law` 由 `R` 变 `证据不足` |

`git reset --hard` 是 R 域**明文列举**的越界形态（R 锚点 reason 里就写着 `git reset --hard / clean -fd / checkout --` 等）。它**不带路径**，所以在门禁眼里「物证不具在」→ 先拦 → 引擎的 R 裁决根本没跑到。

后果是审计层的账：**一次 R 越界被记成「证据不足」**，引擎侧不产生这条 R 事件。

根因：`computer/36` 注释里的那句假设——「越界目标（如 `rm -rf /`）物证仍具在，放行给引擎 R 锚点裁决」——**对 R 域自己列举的 4 个例子里的 3 个不成立**（`git reset --hard` / `git clean -fd` / `git checkout --` 都不带路径）。假设只被 `rm -rf /` 这一个例子验证过。

⇒ 同样**挂账**（同属取舍：要么让门禁在前置位上重跑一遍 R 判定，要么接受 law 降级），不擅动。

> 两处都不是「引擎逻辑错」，是**窗口层新加的这一道门禁自己的边界**。我提出来，是因为它刚上线、还热——早说比晚说便宜。
