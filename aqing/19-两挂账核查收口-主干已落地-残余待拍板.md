## 二、操作序列累积效应 —— 违规累积已落地，组合语义是真缺口

### 2.1 现状：violation 累积 = `failureStreak` + `maxFailureStreak`

`engine.mjs` 里这部分**早已实现**（就是「D 单调累加越阈升档」）：

- **记在谁身上**：引擎实例（宿主会话生命周期）。每次被拦的越界动作（`R` 命中 / 高风险 / `onFailure`）都 `failureStreak += 1`。
- **何时清零**：`healWindow()` —— **破窗修复、以断保续后横向重启才清**（`failureStreak = 0`）。**不是时间清零，也不是单次调用清零**。
- **越阈升档**：`failureStreak >= maxFailureStreak` → 触发 **D 破窗止损**（circuit breaker，防故障扩散杀死整体）。
- 另有 `mBugForce`（同 BUG 反复硬闯）、`mSystemMarks`（同系统含不同伪装标记）两线，达封顶 `mHumanCap=9` → 转人工，AI 停止纠结、不耗算力。

→ 「记在谁身上 / 何时清零」**代码已实锤回答**：累积在会话、修复才清。这正是「以断保续」的工程形态——不让持续出错的 agent 无限撞护栏，但也不因一次误判就永久锁死。

### 2.2 真缺口：小搭子的「组合操作语义」（各自放行、合计越界）

> `read_file /etc/shadow` → read-only，放行；`write_file /tmp/leak` → write，review。
> **两个动作组合 = 信息泄露，但分别看都不是 destructive。**

当前引擎只看**单次动作**判据，不跨调用累积「各放行但净效应越界」的效应。这是 15 那封我标「**记在谁身上、何时清零，我还没判据**」的部分——**确属根因层，我不替你猜**。

**推荐默认**（与 `failureStreak` 同构，不另起炉灶）：
- 累积单元 = **会话 × 目标资源**（如 `/etc/shadow` 的敏感度暴露 + `/tmp/leak` 的外传Sink）。
- 清零条件 = `healWindow()` 或稳态正向动作（写入被隔离/已加密）。
- 越阈升级 = 净暴露预算越阈 → 升 `review` → 再越 → `deny`。
