## 一、你说对了一半：同一根枝，但**方向相反**

你写：

> psi 的问题是自己输出伪零（下游理解成"效应为零"）；overlap 的问题是把不可识别的标记成可识别。前者误导性更强。

这个观察是准的。但我要把它换成判据层的说法：

- **psi 的失效方向是 fail-open** —— 判不出的时候，它**给出答案**（`psi: 0`），而且这个答案是"效应为零"，看上去完全合理。
- **overlap 的失效方向是 fail-closed** —— 判不出的时候，它**拒绝**（判为不可识别 → 交 review），方向是保守的。

**同一条主干缺失（类型级闸门不在位），在两个落点上的失效方向相反。** 这不是"两片叶子挨着剪"的差别，这是**同一处结构缺陷的两种相反临床表现**。

---

## 二、但 overlap 的 fail-closed 是**运气**，不是设计

这是我这封最想说的一条。

你说 overlap 的 `null / false / [] / ''` "碰巧被 `0 < 0.05` 拦住了"。**"碰巧"这两个字是关键，但你只当它是个附注，我把它当成判据。**

我实测了：把 overlap 的下界阈值从 `0.05` 改成 `0`（这在业务上是完全合理的一次调整——"重叠率低于 0 才算离群"，逻辑上无懈可击）：

| 值 | 现网 `<0.05 / >0.95` | 改成 `<0 / >0.95` |
|---|---|---|
| `null` | 拦 ✅ | **放行 ❌** |
| `false` | 拦 ✅ | **放行 ❌** |
| `[]` | 拦 ✅ | **放行 ❌** |
| `[0]` | 拦 ✅ | **放行 ❌** |
| `''` | 拦 ✅ | **放行 ❌** |

**阈值挪一下，全部从 fail-closed 翻成 fail-open。**

所以结论是硬的：

> **靠运气的保守，不是保守。**

它现在保守，是因为 `Number(null) = 0` 恰好落进了 `< 0.05` 这个区间。区间是业务参数，随时会调；**把安全性建立在业务参数的偶然取值上，等于没有安全性。**

这正好是「**硬 ≠ 僵**」那条的反面对照：

- **硬** = 规则与现实因果律同构，所以不随参数漂移；
- **运气** = 恰好没出事，参数一动就出事。

overlap 现在的状态属于后者。修它的理由**不是**"它现在漏了"（它现在碰巧没漏），而是"**它现在没漏，纯属偶然**"。

## 三、顺带把 psi 那行的账补平：还有一个崩、一个阴

你 09 里把自己的修法定为 4/7，很诚实。我按**类型等价类**铺开跑了 19 个代表值（不是 7 个值，是 19 个类型代表），结果比 4/7 更糟一点：

**分歧 7 项，其中 6 项漏、1 项崩：**

| 值 | 类型级闸门 | 你的修法 |
|---|---|---|
| `''` / `false` / `true` / `[]` / `[0]` | 缺失 ✅ | **放行 ❌** |
| `10n`（bigint） | 缺失 ✅ | **放行 ❌** |
| `Symbol()` | 缺失 ✅ | **💥 `Number()` 抛 TypeError** |

两条值得单独记：

**1. `Symbol` 不是漏，是崩。** `Number(Symbol())` 直接抛异常——那行修法在试图判定输入的同时，**自己引入了一个新的失败模式**（传感器整体炸掉，不是漏判）。而类型级闸门安全的原因很朴素：`typeof x === 'number'` 在调用 `Number()` **之前**就短路了，`Number()` 根本不会被调到。**顺序本身就是判据。**

**2. `10n`（bigint）最阴。** `Number(10n) === 10`，有限，于是被当成完全正常的数值信源。bigint 是 number 的近亲，"看起来像数"，所以不报错、不异常，只是**安静地给出一个看起来很合理的错答案**。
